升级包为 `trackcheck-0.4.4-beta.1.apk`。后台、熄屏、采样等计数在“测试与报告”查看，主跑步页不显示；下面的后台验收流程保持适用。

# 凌跑助手 0.2.1-beta.1：后台测试

0.2.1 修复了新一轮仍显示旧计数、重启时未采用近期原生查询证据的问题，并恢复下一次查询倒计时。截图中若顶部报错，不能只凭下面的旧计数判断服务仍在运行。

这版把“实跑监测”和“90秒后台与熄屏检查”的查询、计时、打卡判断、语音及辅助传感器交给带常驻通知的 Android 服务。学校网页用于登录和建立查询会话，服务启动后无需网页持续运行。无需无障碍，也不需要重新安装 AutoJs6。

这是待真机验收的后台测试版。电脑端编译和模拟测试通过，不代表你的手机已经通过后台或锁屏测试。原来的“单次接口诊断”“五轮自动验收”仍属于前台对照测试，不能用它们判断后台是否有效。

## 1. 覆盖安装

1. 把 `trackcheck-0.4.4-beta.1.apk` 发到手机，点击安装并更新已有“凌跑助手”。不要先卸载旧版。
2. 打开 App，顶部应显示 `0.2.1-beta.1`。若显示旧版，先确认打开的是新 APK 应用，而非 AutoJs6 脚本。
3. 选择正确早操/晚操，进入 App 内“学校网页”，确认位于已登录的“健身长跑”。不需要把登录凭据复制出来。
4. 如果系统询问通知权限，建议允许，再回 App 重新点击测试入口。通知提供运行状态和停止按钮；拒绝时需回到 App 停止。

## 2. 先做 90 秒检查，无需跑步

首次先关闭定位和步频，减少干扰。如果提示会话识别依据不足，点击“测试与报告”中的“刷新学校页并更新会话”，等学校网页加载完成后再测试；无需先退出账号。保持正常联网，不主动断开 WebVPN 会话。

1. 点“测试与报告”→“90秒后台与熄屏检查”。
2. 先留在 App，完成中文试听确认。等待“后台检查已经开始……”语音、常驻通知和至少一次成功查询。若报错，先导出报告；不要继续切后台。
3. 按手机 Home 返回桌面，保持屏幕亮着约 30 秒。
4. 按电源键锁屏，等待约 40 秒。此时不要强制结束 App 或清理它的进程。
5. 解锁回到 App，等待自动结束。90 秒从服务启动计时，不包含之前的试听时间。检查模式约每轮完成后 10 秒再次查询，不要求固定查询轮数。
6. 界面应显示后台查询次数大于 0、熄屏/非交互查询次数大于 0，停止原因为 `BACKGROUND_CHECK_DONE`。保存本次 JSON。

**通过条件：** 查询成功、两类计数均大于 0、90 秒正常结束。`BACKGROUND_CHECK_COMPLETE` 单独出现不算通过——全程留在 App 也会正常结束，但无法验证后台。两类计数可能重叠，不能相加当总查询数。

检查模式只在开始时提示一次，之后没有声音是预期行为；它用于验证持续取数，不代表后台业务语音已经通过。应查看计数和报告，而不是靠声音判断是否存活。

## 3. 再检查辅助传感器和真实提示

1. 基础检查通过后，可分别开启定位和步频，再重复一次 90 秒检查；户外走动时更容易获得定位和计步回调。
2. 定位、步频都是可选项。允许“使用期间”定位并在 App 可见时启动服务；本版不申请“始终定位”。开启精确定位仍需系统 GPS 可用。未授权时按打卡间隔估算。
3. 查看报告中 `api` 事件的 `motion` 快照，对比熄屏前后 `acceptedFixes`、`stepCallbacks` 是否增长。只看到最终注册状态或非零总数，不能证明熄屏期间持续采样。停止后注册状态为 false 是正常释放。
4. 准备好实跑时，在经过第一个点位之前点“开始监测”，等查询和常驻通知正常后再切桌面或锁屏。按原计划经过 A→B→A，核对新增打卡、监测后半圈/一圈与实际听感。
5. 初次建立基准会播报一次；其后新增打卡、状态变化或达到疑似漏卡条件才提示，重复数据不重复播报。重播按钮由用户主动触发。
6. 圈数按学校累计距离 ÷ 400米折算，中途接入保留已有距离对应的圈数。定位、步频和速度仅用于预测下一次查询时机，不能确认已经打卡。

## 4. 验证停止，并导出

1. 单独再开一次检查，在通知栏点击“停止监测”。通知应消失，返回 App 后原因为 `NOTIFICATION_STOP`，后续成功查询数不再增加。
2. 正常运动结束后再点“停止”，应保留首次结束原因，不改写为 `USER_STOP`。
3. 到“测试与报告”如实标记最近业务播报听到了/没听到，再导出 JSON。导出会停止仍在进行的任务；一次测试导出后再做下一项，避免拿错当前报告。
4. 如果 App 被系统终止，重新打开后点“导出最近一次保存的报告”。系统直接杀进程可能来不及记录结束事件；报告仍写 RUNNING 且事件突然中断不等于服务还在运行。

## 5. 若后台仍然中断

- 记录大约切桌面/锁屏时间、是否有通知、最后错误和当前版本，再导出报告。不要反复清除数据或重新登录来排查进程停止问题。
- 通过 App 的“应用后台/电池设置”打开系统应用详情，检查该 App 的后台活动/耗电管理限制。华为不同系统版本的名称和入口不同，按实际设置允许它后台运行后重测，不必修改其他应用。
- 不把“最近任务清理”“系统强制停止”“重启手机”当作普通切后台。本版不会在系统终止后偷偷重启或自动重新登录。
- 服务最长两小时，网络或业务会话错误会记录后停止，不会无限重试。短时通过后还应分别进行 10 分钟锁屏和实际运动测试，确认较长待机、信号变化及实际语音表现。

反馈：手机型号/系统、版本、测试入口、是否开启定位/步频、切后台与锁屏的大约时间、实际声音、导出的 JSON。无需提供密码、验证码、Token 或 Cookie。

开发参考：[Android 前台服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)、[Android 15 前台服务时间限制](https://developer.android.com/about/versions/15/behavior-changes-15)。前台服务是系统术语，指带运行通知的服务，不要求用户一直停留在 App 界面。

## 0.2.1 针对本次问题的短测

1. 先导出旧版当前报告（如果仍保留），再覆盖安装新版，不卸载。
2. 完成90秒检查：启动成功后先回桌面约20秒，再按电源键让屏幕熄灭约40秒，解锁回来等自动结束。按电源键后停留在亮着的锁屏界面，不等于已熄屏。
3. 观察本轮开始时间、运行/停止状态、下一次查询倒计时，以及后台/熄屏计数。停止后数字不再增长是正常行为。
4. 导出这一轮JSON，再次开始90秒检查。新轮必须从0/0开始，成功后继续增长；再切桌面一次，核对后台次数增加。
5. 若仍是熄屏0，请照实导出新报告，不改计数、不反复重新登录。系统交互状态、真实显示状态、锁定状态各自记录；单独的后台次数或锁定次数不能证明熄屏查询。

新计数：screenOffQueries 表示请求开始时系统非交互或主显示屏为OFF；displayOffQueries 单独统计主显示屏OFF；lockedQueries只表示锁定；screenOffResponseQueries表示响应时非交互/关屏，不能替代请求开始计数。息屏显示可能仍有显示输出，因此保留原始 display 字段区分。screenOffEvents 是系统进入非交互的事件数，不是查询数。

系统若暂停计时：queryStarted / api / screen 事件和 maxHeartbeatGapMs、maxQueryDelayMs 可以帮助区分暂停点；没有新JSON不能判定旧截图属于哪一种。参考 [Android对SCREEN_OFF与显示状态的区别说明](https://developer.android.com/reference/android/content/Intent#ACTION_SCREEN_OFF)。
